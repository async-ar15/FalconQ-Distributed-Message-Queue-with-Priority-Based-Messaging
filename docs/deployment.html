Deployment Guide

Cluster Configuration

FalconQ brokers discover each other via a `config.yaml` file. Each node must be uniquely identified by its node_id and aware of the HTTP addresses of its peers.

node_id: broker1
http_port: 8080
peers:
  - id: broker2
    address: http://localhost:8081
  - id: broker3
    address: http://localhost:8082

Consistent Networking

Ensure that the peer addresses are fully resolvable by all nodes in the cluster. In Kubernetes, this typically maps to a Headless Service.

Containerized Deployment

For isolated testing, you can run the cluster using Docker Compose. This simulates network latency and prevents local port collisions.

docker-compose up -d --scale broker=3

Kubernetes (Production)

For true production scale on AWS EKS, GCP GKE, or Azure AKS, FalconQ should be deployed as a StatefulSet.

  • StatefulSets: Guarantee stable network identities (e.g., falconq-0, falconq-1) which is critical for Raft consensus.
  • Persistent Volumes (PVCs): Ensure that the BadgerDB commit log survives pod restarts. Map a highly-available block storage (like AWS EBS gp3) to the /data directory inside the container.
  • Headless Service: Used to bypass standard load balancing so peers can communicate directly with each other via their DNS records.
